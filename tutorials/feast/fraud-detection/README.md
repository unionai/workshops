# Fraud Detection with Feast + Flyte

A fraud detection ML pipeline that uses **Feast** as a feature store and **Flyte** for orchestration. Uses the Kaggle Credit Card Fraud Detection dataset (284K transactions, 492 frauds).

```
fraud_detection_pipeline (orchestrator)
  ├── prepare_training_data  → fetch features from Feast offline store
  ├── train_model            → XGBoost classifier with class imbalance handling
  └── score_transactions     → materialize to online store + score samples
```

**Feast** manages features across training and inference — the same features used to train the model are served in real time for scoring. This prevents training-serving skew, one of the most common ML production bugs.

## Step 1: Prepare the Data

Download the dataset and generate feature Parquet files.

```bash
python prep.py
```

This will:
- Download the Kaggle Credit Card Fraud dataset via `kagglehub`
- Engineer features: `hour_of_day`, `amount_log`, synthetic `user_id`, `event_timestamp`
- Compute per-user aggregates: `txn_count`, `mean_amount`, `std_amount`, `max_amount`
- Save to `data/transactions.parquet` and `data/user_features.parquet`

---

## Step 2: Set Up the Feature Store

Register Feast entities and feature views.

```bash
cd feature_repo
feast apply
cd ..
```

This creates the feature registry (`data/registry.db`) with two feature views:

| Feature View | Entity | Features |
|---|---|---|
| `transaction_features` | `user` | `Amount`, `amount_log`, `hour_of_day`, `V1`–`V28` |
| `user_stats` | `user` | `txn_count`, `mean_amount`, `std_amount`, `max_amount`, `total_amount` |

**What Feast gives you here:** The offline store can do point-in-time correct joins — when building training data, each transaction only sees user statistics computed *before* that transaction happened, preventing data leakage.

---

## Step 3: Run the Pipeline Locally

Run the full ML pipeline: fetch features, train model, score transactions.

```bash
flyte run --local workflow.py fraud_detection_pipeline
```

Add `--tui` for a live terminal UI showing the task tree and reports:

```bash
flyte run --local --tui workflow.py fraud_detection_pipeline
```

### What happens

1. **`prepare_training_data`** — Calls `store.get_historical_features()` to join transaction and user features with point-in-time correctness. Reports dataset stats and class balance.

2. **`train_model`** — Trains an XGBoost classifier with `scale_pos_weight` to handle the 0.17% fraud rate. Reports AUC-ROC, confusion matrix, classification report, and top features.

3. **`score_transactions`** — Calls `store.materialize_incremental()` to push features to the online store (SQLite), then uses `store.get_online_features()` to fetch features for sample transactions and scores them. Reports a table of scored transactions with fraud probabilities.

## Key Concepts

### Why a Feature Store?

Without Feast, you'd compute features in your training script and then re-implement the same logic in your serving code. This leads to:
- **Training-serving skew** — subtle differences in feature computation between training and inference
- **Data leakage** — accidentally using future data when building training features
- **Duplication** — same feature logic in multiple places

Feast solves all three: define features once, serve them consistently everywhere.

### Offline vs Online Store

| | Offline Store | Online Store |
|---|---|---|
| **Purpose** | Build training data | Real-time inference |
| **API** | `get_historical_features()` | `get_online_features()` |
| **Latency** | Seconds (batch) | Milliseconds |
| **Data** | Full history, point-in-time correct | Latest values only |
| **Backend** | Parquet files | SQLite (local) / Redis (prod) |

### Class Imbalance

Only 0.17% of transactions are fraudulent. The model uses `scale_pos_weight` to compensate — this tells XGBoost to weight fraud examples ~577x more than legitimate ones during training.

## Make It Your Own

- **Try different models** — swap XGBoost for `RandomForestClassifier` or `LightGBM` in `workflow.py`
- **Add features** — create new `FeatureView` definitions in `feature_repo/features.py` and re-run `feast apply`
- **Tune the threshold** — the default 0.5 probability threshold may not be optimal. Try lowering it to catch more fraud (at the cost of more false positives)
- **Add on-demand features** — use Feast's `@on_demand_feature_view` to compute features at request time (e.g., current amount vs user's average)
- **Switch to Redis** — change `online_store.type` in `feature_store.yaml` from `sqlite` to `redis` for production-grade latency
